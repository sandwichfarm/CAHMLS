# Plan 25-01: Publish the SDK to JSR through verified CI

## Must-haves

1. **JSR-01:** The real JSR CLI accepts `@sandwich/cahmls@0.1.0` from the SDK source tree, with all ten existing runtime entry points and their dependencies, without UI/application imports or generated-output dependence.
2. **JSR-02:** CI performs a publish dry run on the same source/configuration that will be published. Manifest verification detects package name, version, and export-map drift.
3. **JSR-03:** A dedicated GitHub workflow publishes only after successful `CI` from a trusted same-repository push to `master`/`main`, checks out the successful SHA, and uses OIDC with job-scoped minimal permissions. Failed CI, PR CI, and other branches cannot publish.
4. **JSR-04:** SDK documentation explains installation under `@sandwich/cahmls`, the unchanged workspace name, one-time registry setup, version bumps, publication triggers, and failure recovery. Registry publication is not claimed without registry/run evidence.

## Ownership and files

- Executor owns `packages/sdk/jsr.json`, `packages/sdk/scripts/verify-package.mjs`, `.github/workflows/ci.yml`, `.github/workflows/publish-jsr.yml`, `packages/sdk/README.md`, and `docs/guide/getting-started.md`.
- Executor may add a root `sdk:verify-jsr` script in `package.json` if useful; otherwise use the pinned CLI command directly in workflows and documentation. Do not stage the user's original-checkout `package.json` edit.
- If the real CLI reports missing explicit exported types, executor may add only the necessary type annotations in the exact SDK source files named by the diagnostic. Record these files and repeat their relevant checks. No protocol or runtime behavior changes.
- Orchestrator owns `.planning/PROJECT.md`, `REQUIREMENTS.md`, `ROADMAP.md`, `STATE.md`, and this phase's check/verification/shipping artifacts.

Commit when the clean-checkout dry run and workflow validation pass. Use a focused CI commit.
